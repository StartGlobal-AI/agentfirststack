### Security

- **Abuse handling: capability pauses, abuse reports, a signup proof of work, an Acceptable Use Policy** (hardening round after an external review). Strong abuse signals now pause one capability automatically; suspending an account stays a person's decision.
  - **Capability pauses** (`@afs/shared` `capabilityPaused()`, `capabilityPausedError()`, `requestCapabilityPause()`): `mail.send`, `mail.inbox_create`, `tags.custom_code`, `replay.share_links`, `analytics.share_links`, one row per account and capability in the identity DB (`capability_pauses`, site migration `0012_abuse.sql`), cached a minute per isolate. Services answer `403 capability_paused` with the reason and an appeal address, and pause through the site's `POST /v1/internal/pauses` (service binding + `INTERNAL_TOKEN`), which emails the project's people (account email, always sent) and `OPERATOR_EMAIL` at once; without a binding the row is written directly and the hourly cron emails it. The operator lists, pauses and lifts with `GET /v1/admin/pauses`, `POST /v1/admin/accounts/:id/pauses`, `DELETE /v1/admin/accounts/:id/pauses/:capability` (`pnpm afs pause`, `pnpm afs unpause`); after a lift, automatic re-pauses wait `PAUSE_LIFT_GRACE_HOURS` (default 24).
  - **Abuse reports**: `POST /v1/abuse-reports {url_or_resource, kind, details, contact?}` (no account, no captcha; `ABUSE_REPORTS_HOURLY_LIMIT` per network, default 5, `ABUSE_REPORTS_DAILY_LIMIT` for the deployment, default 500; the same report within a day is `200 existing: true`), MCP `afs_report_abuse`, and a form at `/report-abuse` (`?url=` prefills it). Phishing and malware are emailed to the operator at once (`ABUSE_REPORT_EMAILS_PER_DAY`, default 20); all are in the daily summary and `GET /v1/admin/abuse-reports`.
  - **Signups past the deployment-wide breaker** get `429 proof_of_work_required` with a signed `challenge` and `difficulty` (SHA-256 leading zero bits, 20 by default, `SIGNUP_POW_DIFFICULTY`, rising one bit each time the hour's count doubles past `SIGNUP_GLOBAL_HOURLY_LIMIT`, at most 4 more) and ready-made `solve.node` / `solve.python` commands, instead of `429 signups_paused` for everyone; a signup with a valid solution proceeds (per-network limits still apply, one signup per challenge, valid 10 minutes). People creating projects from the dashboard are counted but never held by the breaker (they have `PROJECTS_PER_USER_DAILY_LIMIT`).
  - **Acceptable Use Policy** at `/acceptable-use`, linked from the terms, every footer, llms.txt (new section 13) and the setup prompts, which tell agents to read it.
  - **Reputation checks in the operator's daily summary**: Google Safe Browsing for the apex and service hosts (`SAFE_BROWSING_API_KEY`), the Spamhaus DBL through DNS over HTTPS (`SPAMHAUS_DQS_KEY`), the mail service's deployment-wide bounce and complaint rates, worst accounts first (mail's `GET /v1/admin/delivery-health`, read over the service binding), plus `REPUTATION_DOMAINS`; and the day's pauses and abuse reports. The summary is never held back by the per-address daily email cap.
  - Our own site serves `/_r/*` to replay the way the first-party edge does (`INTERNAL_TOKEN` + `x-afs-edge-host`), so its recorder loads and uploads first-party.
  - The setup check gains `replay.proxy_key` (failing while replay uploads arrive through a first-party proxy without, or with a wrong, replay proxy key in the last 7 days; from the replay site it already reads).
  - Attack emails and banners say what tags now does: under attack only quarantined traffic (data-centre and over-share networks) loses its conversions, and only protection `strict` holds every browser conversion.
  - Mail: `mail.send` pauses on the last hour's bounce or complaint rate (`SEND_PAUSE_BOUNCE_PERCENT`, `SEND_PAUSE_COMPLAINT_PERCENT`, `SEND_PAUSE_MIN_SENDS`), `mail.inbox_create` on an inbox-creation burst (`INBOX_CREATE_BURST_PER_HOUR`); `GET /v1/admin/delivery-health` gives the deployment's rates, worst accounts first (the operator summary reads it). Mail and tags have a `SITE` service binding for the pause route.
  - Tags: custom code is scanned at publish (a strong match pauses `tags.custom_code`), scans and destination tests get daily budgets (`MAX_SCANS_PER_ACCOUNT_PER_DAY`, `MAX_SCANS_PER_DAY`, `MAX_DESTINATION_TESTS_PER_ACCOUNT_PER_DAY`, `MAX_DESTINATION_TESTS_PER_DAY`), and a spike needs `SPIKE_MIN_NETWORKS` (20) distinct networks to count as an attack.
  - Replay: per-site daily budgets (`MAX_CHUNKS_PER_SITE_PER_DAY`, `MAX_BYTES_PER_SITE_PER_DAY`, `MAX_DERIVED_PER_SITE_PER_DAY`) so a flooded site stops alone, bytes per network per site (`MAX_BYTES_PER_IP_PER_SITE_PER_DAY`), heatmap images for claimed accounts only, a per-site proxy key for `/_r/*` proxies, and share-link players link to `/report-abuse`.

- **Tags: browser test traffic (`?afsa_debug=1`, preview, `afst('test', true)`) never reaches an ad platform as a real conversion.** The tags runtime now honours the stack-wide test flag: `?afsa_debug=1` marks the tab (sessionStorage `afsa_debug`, the key the analytics tracker uses, so a flag set by either script holds for both; `?afsa_debug=0` ends it), and so do `afst('test', true | false)` and preview links (`afst('get', 'test')` reads it). In test traffic the browser's ad and vendor pixels (GA4, Google Ads, Meta, TikTok, LinkedIn, UET, Reddit, X, Pinterest, Snap, image pixels) don't fire, in preview too; they're reported as `test_skipped` in the preview log and in `GET /tag-stats` (and left out of `never_fired`). The analytics tag runs as analytics test traffic, custom code still runs, `live_only` tags are skipped. `/collect` hits carry `test: 1`; the server treats them (and any hit with a preview token, valid or expired, or `afsa_debug=1` in its page URL) like preview hits: each destination's test mode or a skip, analytics `debug: true`, webhooks `"test": true`, event log rows `test: true`, and no visitor is created, updated or joined. An expired preview link keeps the tab test traffic. A test hit from a headless browser (Playwright, Puppeteer) is kept, as analytics does; crawlers are still dropped. Before, `?afsa_debug=1` was ignored by tags, so an agent's verification clicks were sent to the ad platforms as real conversions, and pixels fired for real even in preview.

- **Tags: the event log keeps no raw visitor data.** It stores a shortened network (/24 or /48), country, region and device class, never the raw IP, user agent, city or postcode; raw values live only in pending delivery messages. Container Durable Objects scrub conversions stored by older code on their next start (schema version 4). The proxy key is returned only by `GET /install?proxy=1`, to full-access keys.

- **Analytics wave 2 review** (independent review of the wave 2 diff; no cross-tenant path found, signature checks sound):
  - Stripe backfills catch Durable Object errors per site (a suspended account or full site pauses, anything else fails with its message), take turns (least recently worked on first), share one exchange-rate table per cron run (one D1 query per currency), and stop the subscriptions stage after 200 pages with a `truncated` note.
  - Share links: temporary (OAuth) tokens and read-only keys list them without `url` or `token`; wrong passwords are limited per hashed IP and link (10 per 15 minutes) and per link (200 an hour), 429 with `retry_after`, checked before PBKDF2, never blocking viewers who already unlocked; the unlock form body is capped at 4 KB; the unlock cookie is SameSite=Lax.
  - Imports, cost rows and crawler hits are refused on a full site (507 `storage_full`); crawler hits gain account-wide and deployment-wide daily budgets (`MAX_CRAWL_HITS_PER_ACCOUNT_PER_DAY`, `MAX_CRAWL_HITS_PER_DAY`).
  - LemonSqueezy: without a secret, connect generates one (40 characters) and shows it once; a chosen one needs 20+ characters. Past 20 bad signatures in 10 minutes for a site, Polar, Paddle and LemonSqueezy webhooks answer 429 to further bad ones; correctly signed deliveries always go through.
  - Browser user properties are opt-in (`browser_user_props`) with their own key budget (`MAX_BROWSER_USER_PROP_KEYS_PER_SITE`, default 20), so they can never use up server keys; user properties are purged with retention.
  - The cross-domain linker binds `_afsa` to the browser (FNV-1a of user agent, id and minute), accepts it for 2 minutes and removes it from the URL; `afsa('consent', true)` sends the pageview only on the change to granted.
  - Stripe: deleting a site deletes the webhook endpoint we created, reconnecting with another key deletes the old endpoint, and restarting the backfill needs the project's own key.

- **Pre-launch review** (two independent reviews of the whole codebase before the repo went public). Identity and control plane:
  - Creating a project while connecting an app over OAuth goes through the signup gate (`SIGNUP_MODE`, network and deployment-wide counts) plus `PROJECTS_PER_USER_DAILY_LIMIT` (default 5).
  - Keys made with a person's dashboard key are revoked when that person leaves; a connected app's token revokes only its own tokens; each OAuth refresh revokes the access tokens issued before it.
  - Signup refuses cross-site browser requests; claim links die with the key that asked for them; Google sign-in state is a `__Host-` cookie; OAuth redirect URIs can't point at the platform's own hosts.
  - Auth and account standing no longer fail open on database errors; internal calls can't change a suspended account.
  - Deploys turn off `workers.dev` and preview URLs (they'd skip the zone's WAF) and give `ADMIN_TOKEN` only to the site and mail. `deploy/hosted.json` is no longer in the repo.
- **Abuse and cost controls across the platform**, after a full audit of the free hosted service.
  - Account suspension (`pnpm afs suspend`), and lower `UNCLAIMED_*` caps for accounts no person has claimed.
  - Signup limits per network per day (IPv6 grouped by /48) and a deployment-wide hourly breaker; caps on API keys.
  - Daily budgets that never reset for analytics events, tags deliveries and events, replay sessions, chunks, bytes and derived rows, and mail inbound per sender; Workers rate-limit bindings in every app; Cloudflare edge rules on the hosted zone.
  - Replay requires a browser Origin and the page host, verifies domain ownership (snippet on the homepage or a `_afs-verify` TXT record) before more than a trial, purges through per-site alarms, masks more, and quotes transcript fields.
  - Tags: webhooks get matched conversions only, a circuit breaker per destination, the analytics destination is locked to the deployment's analytics, custom code needs a verified domain and a claimed account, and browser hits can no longer claim users or consent.
  - Tags: daily event budgets per account (`MAX_EVENTS_PER_ACCOUNT_PER_DAY`) and deployment-wide (`MAX_EVENTS_PER_DAY`, lower `UNCLAIMED_` value on the same counter), reported to D1 by each container's Durable Object at most once a minute (migration `tags/0007_event_budgets.sql`); past them `/collect` and backend events answer `429 quota_exceeded` until 00:00 UTC.
  - Tags: webhooks can't call any host of the platform (the apex the deployment's hosts share and every subdomain, IP literals and local names too) and their answers are summarized with anything key-like redacted; OAuth access tokens can't add destinations or change their URL or credentials (`403 temporary_credential`); domain proof counts only a real `<script src>` tag on the bare homepage; the Google Ads token cache is keyed by a hash of the full credentials.
  - Analytics: a stricter SQL guard with a query-plan cost bound, hostnames default to the site's domain, storage and retention bounds, opt-in browser revenue.
  - Replay: domain proof counts only a parsed `<script src>` tag (the loader, or the linked analytics tracker) on exactly `https://<domain>/`, which verify fetches itself; a `url` with a query string, fragment or other path never counts, and a loader URL in inline code or echoed text is reported, not accepted (a search page repeating `?s=/r/<id>.js` verified someone else's domain).
  - Analytics: payments, API and signed Stripe webhooks alike, count against the site's, account's and deployment's daily event budgets (an account picks its own signing secret; past them Stripe gets `429` and retries), and the Stripe delivery status is written at most every 5 seconds per site.
  - Analytics: `replay_site_id` is set only by the replay service over internal auth (`403 replay_link_from_replay` for API keys), so a site can't load another account's recorder.
  - Analytics and replay: OAuth access tokens can't create share links or connect Stripe (`403 temporary_credential`), since those outlive the token.
  - Analytics: share links need a verified domain: verify now proves it (the tracker in a `<script src>` tag on exactly `https://<domain>/`, or DNS TXT `_afs-verify.<domain>` = `afs-analytics-site=<id>`; migration `analytics/0009_domain_verification.sql`). Share pages name the verified domain, never the site's free-form name, say the numbers come from the site's own tracker, and show "Unverified site" after a domain change.
  - Mail: waits hibernate and are capped, attachments can't leak in R2, per-sender caps, `latest-code` trusts only authenticated mail from the exact domain, forged `Authentication-Results` and mailing lists no longer unlock replies.
  - Mail: extraction is linear on hostile HTML and text (no backtracking regex; at most 512 KB of each body is read), the per-sender cap runs on the headers before the body is parsed, the daily inbound quota counts only stored mail (in the commit, so killed or concurrent deliveries can't use it up), and unauthenticated mail shares one per-sender allowance; a stored-bytes cap per account (`MAX_BLOB_BYTES_PER_ACCOUNT`, default 1 GiB / 256 MiB unclaimed, `"0"` = off; `Mailbox full` at SMTP; `storage` in `GET /v1/inboxes`) with received attachments kept once and served from the raw MIME (migration `mail/0010_blob_storage.sql`); webhooks can't call the platform's own domain or subdomains and use `http://localhost` only with `DEV_MODE=true` (re-checked before each delivery); OAuth access tokens can't create webhooks (`403 temporary_credential`).
  - Site: removing a member revokes their keys and invites, OAuth tokens can't mint permanent keys, gateway batches are capped, an open redirect is fixed, and the session cookie is now `__Host-` prefixed (everyone signs in again once).

### Added

- **First-party by default.** The full setup installs the first-party proxy (analytics `/_a/*`, tags `/_t/*`, with each one's proxy key) as a step, and the direct snippet only where a platform can't proxy; our own pages serve analytics and tags from agentfirststack.com (`site/src/first-party.ts`). The homepage's "Server-side by default" section claimed ad blockers can't lose conversions; it now says which conversions that holds for. The server-side guide said the same; fixed. Test traffic reaches ad platforms only in their test modes (Meta says test events may still be used), stated plainly in llms.txt.
  - **First-party domains** (Cloudflare for SaaS): `POST/GET/DELETE /v1/first-party-domains[/:hostname]` on the site (MCP `afs_add_first_party_domain`, `afs_list_first_party_domains`, `afs_remove_first_party_domain`). A subdomain of the customer's site (`edge.example.com`) with one CNAME to the deployment's fallback host serves the whole project's collection: analytics at `/_a/*`, tags at `/_t/*`, replay at `/_r/*`, no server code. The site creates the custom hostname (HTTP DV certificate) and a Worker route for it, answers with the DNS record, the snippets that use it and next_steps, refreshes the status from Cloudflare on GET (at most every 30 s per hostname), refuses apexes, the site itself, hosts outside the project's sites and the platform's own zone, warns on labels filter lists target (analytics, stats, track, ...), and removes both on DELETE and when a project is purged. Same hostname again is `200 existing: true`, another project's `409`. Fair use: `MAX_FIRST_PARTY_DOMAINS_PER_ACCOUNT` (and `UNCLAIMED_`). Off (`503 not_configured`) without `CF_SAAS_API_TOKEN`, `CF_SAAS_ZONE_ID`, `CF_SAAS_FALLBACK_HOST` and `CF_SAAS_WORKER` (docs/self-hosting.md). Migration `site/0011_first_party_domains.sql`.
  - **The edge**: the site Worker dispatches a first-party domain before any other route, with the visitor's IP and geo, cookies and visitor-sent `x-afs-*` stripped, and `x-afs-internal` + `x-afs-edge-host`; `edgeHost()` in `@afs/shared` (service binding + constant-time token, no account) lets analytics ingest, tags `/collect` (and the script's consent region) and replay ingest trust it like a valid proxy key. Through it, analytics answers the tracker with a first-party replay loader (`https://<hostname>/_r/r/<rsite>.js`), and tags reads the forwarded geo and network too.
  - **First-party is the default everywhere**: analytics, tags and replay install and create answers lead with a `first_party` block (a first-party domain, then the path proxy, then the direct snippet as a last resort; every existing field kept) and next_steps lead with it; llms.txt's full setup prefers a first-party domain when DNS can be changed (otherwise it's one record waiting on the owner), with a reference section; the landing page prompt asks for it.
  - **Setup check `analytics.first_party`**: fails while the latest browser events go straight to the analytics host (with the fix: add a first-party domain, or swap to the active one), waits on the owner while a first-party domain waits for its CNAME, warns when the latest came first-party but some went direct this week. Analytics counts each day's browser events by path in the usage upsert it already makes (`direct`/`proxy`/`edge`, the edge hostnames, the latest of each), shown as `data.collection_last_7d` in `GET /v1/sites/:id` (SiteDO schema 13). Setup catalog version 5, so set-up projects hear about it.
  - Analytics `install?framework=nextjs` is a plain `<script defer src="/_a/s.js">` in the root layout's `<head>` (Pages Router: `_document.tsx`) plus `proxy.ts`, not `next/script` with `afterInteractive`, which isn't in the server HTML, so verify never found it and a Next.js site couldn't verify from its homepage. Replay's Next.js snippet is a plain `<script defer>` too. Verify passes a tracker on a first-party domain once events arrived through it (the platform can't fetch its own zone).

- **Attack protection for customers' sites and containers.** Site and container ids are public, and daily budgets were per site, account and deployment only, so one network could use up a site's budget and real visitors' events were dropped until 00:00 UTC. Now (analytics and tags, `shared/src/protection.ts`):
  - **A network's daily share**: past `MAX_EVENTS_PER_NETWORK_PER_SITE_PER_DAY` (analytics; hosted 2000, unclaimed 500) or `MAX_EVENTS_PER_NETWORK_PER_CONTAINER_PER_DAY` (tags; 1000 / 200) browser events from one network (IPv4 address or IPv6 /48, counted by a keyed daily hash, never stored), the rest of its day is quarantined, not counted against the budget. Server events with a key are never quarantined.
  - **Attack mode**: a 15-minute window at 10x the site's usual rate (and 1000+ events) puts it under attack for an hour after the last spike: browser traffic from data-centre networks is quarantined, and tags doesn't forward browser conversions to ad platforms (backend conversions keep flowing). `protection: auto | strict | off` on sites and containers (REST and MCP).
  - **Quarantine**: analytics stores quarantined events with `debug = 2` and a reason (`debug=quarantined` on any read; `include` now means test traffic but not quarantine), their own daily cap (`MAX_QUARANTINED_EVENTS_PER_SITE_PER_DAY`, 20000 / 2000), kept 7 days; `GET /v1/sites/:id/quarantine`, `POST .../quarantine/release`, `POST .../quarantine/purge` (MCP `get_quarantine`, `release_quarantine`, `purge_quarantine`). Tags logs quarantined hits (`status: quarantined`), never delivers them; `GET /v1/containers/:id/quarantine` (MCP `get_quarantine`).
  - **Telling people**: `protection` on `GET /v1/sites/:id` and `GET /v1/containers/:id`; `attacks` in each service's `GET /v1/usage` and the site's (MCP `afs_get_usage`); a `site_attack` email (alerts) once per episode with a prompt for the agent; a banner on the project Overview and the analytics and tags tabs.
  - Migrations: analytics D1 `0020_attack_protection.sql` and DO schema 12; tags D1 `0010_protection.sql` and DO schema 5.
- **Live analytics.** `GET /v1/sites/:id/realtime/stream` (analytics) is a WebSocket held by the site's Durable Object with the Hibernation API: a snapshot on connect, then an update within a second of new events (at most one a second per site), with `online`, the 5- and 30-minute counts, new pageviews and the latest pageview's page, place and source. 20 streams per site (a new one closes the oldest), 6 hours each; `ping` is answered without waking the object. Realtime gains `online`: visitors seen in the last 5 minutes minus those who closed the page. The tracker sends `l: 1` on an engagement beacon when a page unloads for good (pagehide, not the back/forward cache), even with under a second visible; such leave-only beacons don't count against the daily budget (DO schema version 11, `live_leaves`). Tracker: 5293 bytes, 2825 gzip (+33 / +17). The dashboard opens the stream through `GET /dashboard/projects/:id/live/analytics/:site` (signed in, a member, same Origin), shows the count in the tab title, pings the Online dot on each pageview and shows the latest visitor under the KPI row; it polls every 10 s without the stream and once a minute with it, and refreshes when you come back to the browser tab.

- **Deleting a project.** The owner deletes it in Settings, General (typing its name). An unclaimed project's own agent can delete it with `DELETE https://agentfirststack.com/v1/me {"confirm":"<id>"}` or the `afs_delete_project` MCP tool. A claimed project's agent gets `403 owner_required`. Deleting does four things at once:
  - Every key and OAuth token answers `403 project_deleted`, with the restore date in the hint.
  - Tracking, recording, inbound mail and forwarding stop within a minute (account standing reads it as stopped).
  - Unused claim links die, and members lose the project.
